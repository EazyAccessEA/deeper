## T1

```text
Write one Instagram caption for a jar of borage honey.

Before writing, ask me for: a photo of the jar, the label text, the harvest place and date, anything the beekeeper said about this batch, and whether there is a pollen analysis confirming it is borage-dominant. If there isn't, don't call it "borage honey" as a fact; phrase it as the beekeeper's account or ask me how to handle it.

Write it like a food copywriter for a small producer:
- Build it on one concrete fact about this jar (place, timing, how it looks, tastes or pours), not stock honey adjectives. Borage honey is typically pale, mild and slow to crystallise; use only what matches the actual jar.
- Put the hook in the first ~125 characters, because Instagram cuts there. Read it as it appears in the feed.
- Do a proper tasting note first (colour in daylight, aroma, texture, finish) and draw the caption's details from it.
- If I can share the account's Instagram Insights, look at which past captions earned the most saves and comments and match that length and voice.

Check before handing it over:
- The first 125 characters alone must tell a reader it's borage honey and give one specific reason to want it. If not, rewrite.
- Every factual claim (floral source, location, process) must be backed by the label, the beekeeper or a pollen analysis.
- After posting, the test is saves plus comments at 48 hours versus the account's median for its last ten posts; below median counts as a miss.

Deliver one caption, with hashtags only if the account normally uses them.
```

## T2

```text
Evaluate the typesetting of my book manuscript and improve it. I think the inner margins look too large.

Before changing anything, ask me for: the source file (InDesign, LaTeX, Word or PDF export), the trim size, page count, binding type (perfect-bound, sewn, saddle-stitched, ebook), paper, and the printer's template or gutter requirement.

Work like a book typographer:
- Judge margins on the two-page spread, not the single page, and allow for the gutter the binding will swallow. Check whether the large inner margin is actually correct for this binding and page count before shrinking it. Tell me plainly which it is.
- Set the text block from proportions: inner < top < outer < bottom, with a measure of about 60-70 characters per line. Change the system, not one number at a time.
- Review in the layout program: leading against a baseline grid, hyphenation and justification settings, widows, orphans, rivers, running heads and folios.

Evaluation: list each problem with page references and the reason it matters.

Check the improved version against:
- A printed proof of sample spreads (including one near the middle of the book) at actual trim size, folded or bound. Text must sit balanced across the open spread with nothing lost in the gutter.
- Average measure 60-70 characters; anything outside 45-75 is a fail.
- Zero widows and orphans and no visible rivers in the sample spreads.
- The printer's preflight passes with no margin or safe-area warnings.
- If possible, the printer's prepress team or a book designer reviews the proof.

Deliver the evaluation and the improved manuscript file, nothing else.
```

## T3

```text
Help me sell my VW Polo and buy a new car, perhaps a Golf.

Before advising, ask me for: the Polo's registration document details (year, engine, trim), mileage, service history, inspection/MOT reports, tyre and brake condition and any damage; my country; how many miles a year I drive and what for; who travels with me; my budget, and whether I'd pay cash or finance.

Work like an experienced independent car buyer and seller:
- Treat the sale and the purchase as two separate deals. Never let a trade-in figure hide the price of the new car.
- Price both cars from actual sold prices for the same spec, year and mileage, not asking prices. Use trade guide values for my country and get at least three instant-buyer or dealer quotes for the Polo.
- Before settling on a Golf, check it against my real usage with a total cost of ownership comparison over my expected holding period (depreciation, fuel, insurance, tax, servicing, finance interest) for the Golf and one or two realistic alternatives, including keeping the Polo.
- For the car I buy: full history check and an independent pre-purchase inspection.

Checks:
- Sale: at least three written offers; accepted price at or above the median sold price for that spec. Selling below the lowest written offer is a fail.
- Purchase: independent inspection and history check with no unresolved findings; total cost of ownership within my budget. Buying without an inspection, or a deal where trade-in and discount can't be separated, is a fail.

The outcome is the Polo sold and the next car bought, nothing else.
```

## T4

```text
Can we move our Next.js app off Vercel to Cloudflare? If yes, move it.

Before deciding, read the repo and the Vercel project (ask me for access if you don't have it): package.json (Next.js version), next.config.*, vercel.json, middleware, every route handler and its runtime export, uses of next/image, revalidate/ISR, unstable_cache, Node-only APIs, and any Vercel KV, Blob or Postgres SDKs; plus the Vercel env vars, domains, cron jobs and recent traffic and error logs.

Work like a platform engineer:
- Produce an inventory of every Vercel-specific feature in use and map each to its Cloudflare equivalent (OpenNext Cloudflare adapter on Workers, R2, KV, D1, Cron Triggers, Cloudflare Images) or mark it a gap. Answer "can we" from that inventory, with the gaps and their cost.
- If yes: deploy with @opennextjs/cloudflare and Wrangler to a Cloudflare preview while Vercel stays live. Cut DNS only after the checks pass, with a rehearsed rollback.

Checks (run them, don't assume):
- The same end-to-end suite (existing tests plus Playwright over the key routes) passes against both the Vercel production and the Cloudflare preview.
- Every route in the inventory returns the same status and content on both.
- p75 TTFB and Core Web Vitals on Cloudflare are no worse than Vercel for the same pages; also a load test at peak traffic from the logs.
- DNS rollback rehearsed before cutover.
- For 7 days after cutover, error rate stays at or below the Vercel baseline.
Any route that behaves differently, a slower p75, or an untested rollback is a fail.

Deliver the answer and, if yes, the app running on Cloudflare. Nothing else.
```

## T5

```text
Tidy my Downloads folder.

Start from the actual contents: list every file with size, type and modification date, and ask me where things should go (my Documents structure, cloud drive). If you can't read the folder, ask me to paste a listing.

Work like a records manager:
- Find duplicates by content hash (shasum or fdupes), not by filename.
- Sort each file by purpose: keep and file in its proper place; installer for something already installed; already stored elsewhere (same hash); junk.
- Move, don't delete. Anything to be removed goes to a staging folder or the Trash for me to review. Flag anything that may be the only copy (contracts, receipts, licence keys) and ask before touching it.

Checks:
- Report file count and total size before and after.
- Every removed file has an identical-hash copy elsewhere or sits in the staging folder/Trash for my review.
- I name five files at random and can find each in its new place.
Any file whose only copy was removed without my review is a fail.

Deliver a tidied Downloads folder, nothing else.
```
